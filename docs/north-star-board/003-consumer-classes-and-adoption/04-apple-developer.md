# Apple Developer Seat — Record 003

## 1. Verdict

The product's onboarding story is genuinely fixed and the update story is not. P5 shipped and should be ratified; P3 and P4 are cheap, correct, and mostly outside my lens's stress. P1 correctly names real pain but proposes the wrong instrument: the friction the owner feels is **step count**, not explicitness, and the repo already holds a ratified, cheaper answer to it (Decision 35's interim relief, issue #16). Worse, class (b) as briefed is not implementable alongside class (a) on a single machine — the pin is compared against the *running* build and there is one machine-wide install, so an auto-updating consumer would put the fail-closed reference consumer into a blocking `runtime_pin_mismatch` the moment it updates. P2's diagnosis is exactly right and its fix shape is half right: scaffolding and product-status accounting land as relief; "loudly nags" and a new readiness severity land as noise on a surface that is already provably unreadable (issue #26: ~65KB, verdict buried, 177 repeats).

The through-line for my lens: this product has twice now shipped a correct mechanism whose *reporting* defeated it — `optional_playbook_output_missing` and the bare `failed: exit 12`. Adding another finding class before fixing the finding surface repeats that mistake a third time.

## 2. Evidence

### P1 — consumer-class segmentation

**The ceremony is real and measurable.** `README.md:262-316` is a seven-step maintainer flow, and step 5 is explicitly *per consumer* with project-level copies: "Repeat this step for every consumer that carries project-level copies… or the pin fails with `workflow_hash_mismatch` (this bit the `gb37a12a0502e` release once before the project-level copies were re-targeted)." The 2026-08-06 wrap records the shape of an actual release as "bump commit → build → publish → uv tool install → workflow installs to ~/.claude AND HTV .claude → pin → readiness verify → commit ~/.claude artifacts in-flow". That is not a ceremony a person should run twice per release, and it has already produced one self-inflicted fail-closed incident.

**But the pain is step count, not explicitness, and the fix is already ratified.** `DECISIONS.md:387` (Decision 35): "the interim relief is mechanical, not contractual: the release flow collapses into a single maintainer command and consumer updates into a single verified command, keeping the explicit-action clause while removing the ceremony." That is issue #16, open, unimplemented, and listed as "optionally implement" in every wrap since 2026-08-06. Two consumers × one `meeting-ingest update` each is not ceremony. P1 proposes to change the contract before trying the mechanical relief the contract already authorizes.

**Class (b) collides with class (a) on one machine.** This is the finding I would not want the board to miss. `src/meeting_ingest/runtime.py:685` compares the pin's `approved_build_id` against the *running* build; a mismatch emits `runtime_pin_mismatch`, and `_finding()` at `runtime.py:458-470` hardcodes `severity="blocker"` — so `blocked`, exit 12. Installation is one machine-wide `uv tool install` producing one console script (`/Users/kmgdev/.local/bin/meeting-ingest`), and `_require_approved_frozen_install` (`runtime_release.py:868-902`) requires the *running* install to already match the receipt being adopted. Consequence: the moment an auto-updating consumer causes a newer wheel to be installed, the fail-closed reference consumer on the same machine is blocked until the owner repins it. The two classes are not independent; they share a runtime. Class (b) as briefed would *increase* the owner's repin work at HTV, not decrease it.

**A second collision: pending handoffs.** Decision 31 (`DECISIONS.md:335`): "Phase 2 must match build, source/tree identity, workflow, install/runtime mode… exactly. A mismatch retains the handoff and never adopts the newer runtime silently." An auto-update landing between phase 1 and phase 2 strands every pending handoff in the inbox. Any class (b) must be quiescence-gated, and nothing in the brief says so.

**Timing under Decision 35's own criteria.** Criterion 2 (three consecutive drift-free releases) is close — 0.2.1 and 0.3.0 both shipped clean; the 2026-07-25 receipt-drift catch and the `gb37a12a0502e` workflow-hash failure precede them. Criterion 1 is far: it requires the Just Works Continuity milestone met, and `docs/product-status.md:41` records Track 4 as "not started; approval-gated" behind OB-002-1. So "wait for the sunset" is not a near-term answer. Decision 35 anticipates this and names the legitimate shortcut: the board also convenes "or the owner declares early intent to broaden" — but its input is a **distribution-transition plan**, and it explicitly reserves the question P1 asks: "Whether client-work consumers retain any explicit-update posture is decided by that board convening, not presumed." P1 is that convening in all but name, arriving without the plan it is supposed to review.

### P2 — shipped-means-running

**The diagnosis is exact, and the mechanism is worse than the brief states.** The brief says readiness "filed the absence at a severity everyone learned to ignore." The code shows three separate mislabels, not one. `readiness.py:60-77` maps `playbook_state_missing`, `playbook_profile_missing`, and `playbook_stale` to the emitted code `optional_playbook_output_missing`; `readiness.py:413-422` stamps every such finding `category="history"`, `severity="warning"`, with remediation text "Review or adopt this historical state separately; it does not block the next safe write." A core feature's total inactivity was reported under a code literally containing the word *optional*, in the *history* category, with remediation telling the reader it is historical. Nobody learned to ignore a severity — they read three labels that all said "ignore me," and were correct to.

**Item 3 (core-inactive severity) will land as noise unless sequenced.** Readiness has exactly three severities and a verdict derived mechanically from them (`readiness.py:178-195`): any blocker → `blocked`; else any warning → `ready_with_history_warnings`; else `ready`. So a new warning-severity finding is invisible at HTV, which already sits at `ready_with_history_warnings` with 177 findings — issue #26 documents that payload as ~65KB of same-code repeats with "the verdict… one field buried in the volume." And at Trace3, which returns a clean `Ready`, one core-inactive warning flips the verdict to `ready_with_history_warnings` — a verdict whose ratified meaning (record 002 addendum 10, OB-002-2) is "historical continuity remains incomplete." On a fresh consumer with no history that is a false statement produced by the fix.

**Item 2 bundles two different designs behind an "or".** "Ingest completion triggers — *or loudly nags* — dependent derivation steps." Scaffolding is unambiguously right and has precedent: 0.3.0's init already scaffolds the meetings root, and 0.2.1 already scaffolds `_playbook-state/` (issue #15). Nagging is the risk. `SKILL.md:263-278` already requires an eight-item completion message per meeting; a per-ingest nag is a permanent tax on the highest-frequency workflow in the product, and a message that appears after *every* successful ingest becomes wallpaper faster than an "optional" finding did. Meanwhile `playbook update` is already an explicit deterministic **full rebuild** (`docs/product-status.md:451`), which means auto-running it is idempotent and safe — the trigger arm of the "or" is technically available and the nag arm is not needed.

**Items 1 and 4 are already grounded.** 0.3.0's release evidence is exactly what item 1 asks for (`docs/sessions/2026-08-30-one-command-init-release.md:40-46`: virgin smoke, HTV repinned, Trace3 repinned). Item 4 is issue #23, which also fixes a live self-contradiction — `product-status.md:236-237` still lists the identity registry and briefing aggregation as "Not complete" while the Layer 5A/5B sections record them implemented. That contradiction is itself evidence for item 4: hand-maintained status prose goes stale, and the 2026-08-17 wrap names it as "part of why the owner could not tell where the product stood."

### P3 — reference consumer as a formal role

Supported by practice: the 0.3.0 measure of done was demonstrated at HTV and Trace3 (session doc, lines 40-46), the corpus-upkeep procedure lives in the consumer's CLAUDE.md (2026-08-30 wrap), and the 2026-08-06 ruling already states "HTV is the reference consumer and show horse… every feature ships active to HTV unless explicitly scoped away from it."

From my lens the gap is what the proposal *omits*: HTV is permanently at `ready_with_history_warnings` with 177 standing findings, so it is a poor clean-room. The thing that actually caught the Trace3 onboarding defect class was a **virgin project**, and 0.3.0's evidence pairs both — "Virgin project: `meeting-ingest init` → Ready… One command, zero flags" alongside the two repins. The role should formalize the pairing that worked, not just the client consumer.

### P4 — third-party redistribution boundary

Nothing in the repo contradicts it, and it costs nothing to state. My lens's only contribution: the trigger as written ("if briefs ever gain other recipients or a consumer class beyond the owner") has no observable state behind it. There is no consumer registry anywhere — pins live in each consumer root, and the channel manifest tracks receipts, not consumers (`runtime_release.py:613-669`). A check-in trigger with no artifact to watch reopens by memory, which is the exact failure the proposal says it exists to prevent.

### P5 — one-command init

Strongest evidence in the brief. The defect it fixes was real and my-lens-shaped: the 2026-08-17 wrap records the owner's own second-consumer onboarding failing with the bare line `failed: exit 12`, root-caused to three separable defects (bootstrap inversion at `pipeline.py:169`, discarded error detail at `cli.py:391`, a fabricated `workflow_hash_mismatch`), and unblocked only by the maintainer hand-walking the full release flow. The owner explicitly rejected both "exempt init from the gate" and "emit better remediation." 0.3.0 shipped the rejection-compliant fix: `bootstrap_consumer_runtime` (`runtime_release.py:957-1040`) selects channel-latest, verifies the running install, installs receipt-verified project-level artifacts, re-inspects that the session resolves those exact bytes, pins exclusively, scaffolds, and gates on readiness — and removes the pin it wrote if a later step fails, so a rerun converges. T2-verified, two independent reviews, deferred hardening recorded as #27. This is the one place in the record where the product got measurably lighter than the work it replaces.

Two scope facts the ratification should carry rather than obscure: init's one-command guarantee holds only on a machine whose approved runtime is already current — otherwise `_require_approved_frozen_install` raises `runtime_build_mismatch` with "Install the approved wheel… and run `meeting-ingest init` again" (`runtime_release.py:895-902`). And `init` never replaces an existing pin (`README.md:327`), so it is a bootstrap command, not a repair command.

## 3. Gaps and risks

1. **Shared-runtime collision (P1, highest).** Class (a) and class (b) cannot coexist on one machine under the current pin-versus-running-build comparison and one machine-wide install. Unaddressed, class (b) converts the reference consumer's next meeting into an exit-12 surprise at an unpredictable moment — the worst possible time for a fail-closed gate to fire.
2. **Mid-workflow adoption (P1).** Auto-update between phase 1 and phase 2 strands pending handoffs by design (Decision 31). No quiescence constraint is proposed.
3. **New-finding-class-before-readable-findings (P2).** Issue #26 is open. Any core-inactive finding added before it lands is provably invisible at the reference consumer, and provably mislabels a clean consumer at the second one.
4. **Verdict-vocabulary collision (P2).** `ready_with_history_warnings` has a ratified meaning from OB-002-2. Routing "a core feature was never turned on" through it corrupts a term the owner has already ratified.
5. **Nag fatigue (P2).** A per-ingest reminder on the product's highest-frequency command reproduces the ignored-signal failure mode on a faster cycle.
6. **No consumer repair path (P5, my lens's standing gap).** A consumer whose installed workflow artifacts drift — the `gb37a12a0502e` case, and the standing open question "there is no local way to tell whether a copy still matches the receipt that placed it" — has no product command. Remediation is a hand-typed `scripts/install-approved-skill.py` invocation with six flags from the README. `init` refuses (existing pin), `runtime pin` re-pins but does not re-render.
7. **Hand-maintained activation accounting (P2 item 4).** Adding an "active-per-consumer-class" column to a prose document that already carries a stale not-complete list will go stale the same way.
8. **Trigger with no artifact (P4).** No consumer registry exists to hang the reopening trigger on.
9. **Bootstrap concurrency and RECORD-derived identity (#27).** Known, accepted, fail-closed rather than silent — but note that P1's class (b) would make item 1 of #27 materially more important, because an unattended updater is exactly the actor whose install-time identity check should not be self-supplied.

## 4. Recommendations in priority order

1. **Implement issue #16 before deciding class (b).** One maintainer `release` command and one consumer `meeting-ingest update` command (fetch → verify → install → repin), both driving the existing verified steps. This is the interim relief Decision 35 already authorizes, needs no contract amendment, and removes the great majority of the felt pain, including the per-consumer step 5 that has already caused one incident. Re-ask P1 after one release has run through it.
2. **Rename the mislabeled codes and their remediation text — today, before any new severity.** `playbook_state_missing`/`playbook_profile_missing` must not emit as `optional_playbook_output_missing` in `category="history"` with "Review or adopt this historical state separately." That one-line class of fix (`readiness.py:60-77`, `413-422`) would have surfaced the 0.2.0 registry gap without any new taxonomy.
3. **Land issue #26 before adding any finding class.** Verdict-only view or same-code collapse. A gate nobody can read is not a gate.
4. **Choose trigger over nag.** Derivation is a deterministic full rebuild, so run it automatically at the end of an ingest *batch* (`session-inbox` / `ingest-inbox` completion), once, not per file — with failure surfaced as a real error. Reserve any user-facing message for the failure case.
5. **If a core-inactive state must be reportable, give it its own verdict-visible term** — not `warning`, not `blocker`, and not routed through `ready_with_history_warnings`. Better: make it structurally rare by scaffolding at init and post-update, so inactivity is a defect to report rather than a standing condition to categorize.
6. **Formalize the reference-consumer role as a two-part gate:** activation evidence at the reference consumer *plus* a virgin-project clean-room run. That is what 0.3.0 actually did, and the clean-room half is what catches the defects a 177-finding baseline hides. Name the fallback when the reference consumer is unavailable, so releases do not block on a client project's state.
7. **Add a consumer repair command** (`meeting-ingest runtime repair`, or let `init --repair` re-render) that re-installs the workflow artifacts from the pinned receipt and re-verifies. Retire the README's six-flag installer invocation as a user-facing remediation.
8. **Bind P4's trigger to observable state.** Whatever registry names consumers and their class (needed by P1 and P3 anyway) is the place a new recipient or consumer class becomes visible; fire the check-in from a change there.
9. **Derive activation state rather than writing it.** Give `readiness` or `status` an activation section and have product-status quote it with a date and build ID, instead of asserting activation in prose.

## 5. What to stop, defer, or simplify

- **Stop** treating "explicit update" as the source of the friction. Explicitness costs one command; the seven-step, per-consumer flow costs the afternoon.
- **Stop** adding reporting categories to a readiness payload that cannot be read at the reference consumer.
- **Defer** class (b) entirely until either (a) #16 has shipped and one release has run through it, or (b) the owner declares early intent to broaden and the board receives an actual distribution-transition plan — the input Decision 35 names.
- **Defer** the nag arm of P2 item 2 permanently; adopt the trigger arm.
- **Simplify** P2 to three items — scaffold, trigger, account — plus the code/remediation rename, and let item 3's severity question be answered by whether anything is still chronically inactive after those land.
- **Simplify** the per-consumer workflow-artifact install out of existence: one command that installs and pins every registered consumer, so "repeat this step for every consumer" stops being a README instruction a human executes.

## 7. Confidence and unresolved questions

**High confidence** on the P1 shared-runtime collision and the P2 severity mechanics — both are read directly from the shipped code (`runtime.py:458-470`, `685`, `776`; `readiness.py:60-77`, `178-195`, `413-422`; `runtime_release.py:868-902`), and both are falsifiable by a five-minute experiment. **High** on P5. **Medium** on P3 and P4, which are governance shapes where my lens contributes ergonomics, not authority. **Medium** on my count of Decision 35's criterion 2 (I read two consecutive drift-free releases, 0.2.1 and 0.3.0, following the 2026-07-25 and `gb37a12a0502e` incidents); the chair and owner hold the authoritative count.

Open questions I could not settle read-only:

1. **Is class (b) meant to run on a second machine or in a second runtime?** If every consumer shares one install, the class distinction is fiction; if the intent is per-consumer runtime isolation (per-project venv or per-consumer tool install), that is a substantial engine change nobody has scoped, and it should be priced before the class is ratified.
2. **Who is class (b) for?** Both current consumers are the owner's. If class (b) exists for a future non-owner consumer, then creating it also fires P4's reopening trigger — the two proposals are coupled and the brief treats them independently.
3. **What does the repin ceremony actually cost per release?** Nobody has recorded minutes. If #16 takes it from an afternoon to two commands, the contract question may simply evaporate; that measurement should precede the amendment.
4. **Is Trace3 client work?** Its class assignment determines whether "auto-updating" means "ships client deliverables from an unreviewed build," which is a different risk than a personal project drifting forward.
5. **Should the installed workflow artifacts carry their own receipt stamp?** This is a standing open question in two wraps, and it becomes load-bearing under any unattended-update model — an updater that cannot locally prove the copy it placed is still the copy in use is the weak link in an invisible-verification story.
